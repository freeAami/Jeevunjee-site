## 2. Posture summary

The Supabase row-level security model is sound. Students are strictly isolated from each other. Anonymous users can only submit. Access codes are strong, single-use and expiring. No SQL injection, formula injection or DOM XSS path was found, and no privileged secret is committed. The weaknesses sat at the edges of that model:

- trustee sign-up trusted an email address with no proof of ownership;
- the public Apps Script inbox would act for any caller;
- anonymous submission and upload paths had no aggregate bounds;
- deletion did not reach applicant files.

All nine records have source-level fixes in commit `045bf1a` (section 8).

## 4. Confirmed finding details

### Anyone who knows an unclaimed trustee email can sign up as a trustee (admin), because the project's setup turns off email confirmation

- **Fingerprint:** `supabase/schema.sql:handle_new_user:admin-email-claim-without-ownership-proof`
- **Source:** `src/portal/api.ts:126`, `supabase/setup.mjs:174`, `supabase/setup.mjs:193`, `supabase/schema.sql:261`, `supabase/schema.sql:238`
- **Lower-trust principal:** Anonymous internet user with the public anon key who knows a trustee email address that has not been claimed
- **Reproduction (local, dummy data):** Inside the sandbox, initialise Postgres 16 and load supabase/tests/supabase_shim.sql and then supabase/schema.sql into a fresh database. Control: insert an auth.users row for a non-listed email with no code and observe JVJ_SIGNUP_NOT_ALLOWED. Insert a dummy trustee email into admin_emails and add a dummy application, a student and an applications-bucket storage object. Insert an auth.users row for the trustee email with an empty access_code, as GoTrue does on signUp when confirmation is off. Check profiles.role and admin_emails.claimed. Then act as role authenticated with that uid and query is_admin(), applications, students and storage.objects, and call issue_access_code. Insert another auth.users row for the same address (the genuine trustee) and observe that it is refused.
- **Conditions:** [system_configuration] Supabase Auth email confirmation is off (mailer_autoconfirm), as supabase/setup.mjs:193 and SETUP.md:43 instruct. [data_state] At least one admin_emails entry is still unclaimed: a listed trustee has not signed up yet, never will, or the address was added later. [authentication_level] Unauthenticated. The attacker needs only the public anon key and URL (committed in .env.production). [environmental_dependency] The attacker knows or guesses the unclaimed trustee address. One route is the Apps Script confirmation replyTo, if ADMIN_EMAILS is set to the same addresses. [timing_dependency] The attacker must sign up before the genuine trustee claims the address.
- **Actual result:** Non-listed control: ERROR JVJ_SIGNUP_NOT_ALLOWED. Attacker row: profiles role=admin, admin_emails trustee@x.test claimed=t. As that uid: is_admin()=t. The reads returned 'JVJ-T-1|Dummy Applicant|{"nic": "DUMMY-NIC"}', 'Dummy Student|DUMMY-NIC-2' and 'applications|incoming/abc/nic-front.jpg', and issue_access_code returned an 8-character code. The genuine trustee's same-address insert failed with a duplicate email error, and a case-variant insert failed with JVJ_SIGNUP_NOT_ALLOWED. GoTrue itself was not run. Autoconfirm turning signUp into an immediate confirmed session is taken from the committed configuration and documented Supabase behaviour.
- **Impact:** Full trustee privileges: read and write of every applicant's and student's PII, read of ID images in storage, the payment ledger and notes, and issuing student access codes. The real trustee is also locked out of their own login.
- **Priority:** medium. Likelihood: low (The attacker needs an unclaimed trustee entry (the setup window, a trustee who never registers, or a later addition), must know that exact address, and must sign up before the trustee does. Source commits no real trustee addresses.). Impact: critical. Confidence: high.
- **Smallest source fix:** Do not grant admin on an email string match alone. Either provision trustee accounts out-of-band (service-role inviteUserByEmail or a magic link to the address) and refuse public sign-up for admin_emails addresses, or require a secret one-time trustee code in the sign-up metadata, checked the same way as the student code. If confirmation can be turned back on (with SMTP configured), also require new.email_confirmed_at in the admin branch, or move the grant to a confirmation-time trigger. Until then, the operator should have each trustee sign up immediately after setup and check that every claimed admin_emails row belongs to the real trustee. Do not reuse the admin_emails addresses as the applicant-facing replyTo; use a shared alias. Regression test: a sign-up with an allow-listed email and no valid trustee code must raise JVJ_SIGNUP_NOT_ALLOWED.

### Deleting an application-derived document leaves the applicant's ID/income file in storage, and re-enrolment brings it back

- **Fingerprint:** `src/portal/api.ts:deleteDocument:applications-bucket-blob-retained-and-resurrected-by-enrol_application`
- **Source:** `src/portal/admin/StudentFile.tsx:408`, `src/portal/api.ts:260`, `src/portal/api.ts:261`, `supabase/schema.sql:482`, `supabase/schema.sql:479`, `supabase/schema.sql:382`
- **Lower-trust principal:** There is no external attacker. This is a lifecycle failure observed from the trustee role against a dummy applicant. The affected party is the applicant whose deletion is not honoured.
- **Reproduction (local, dummy data):** Inside the approved sandbox, initialise local Postgres 16 and load supabase/tests/supabase_shim.sql and supabase/schema.sql. Allow-list a dummy trustee and sign it up. As anon, submit a dummy application with one idFile and insert the matching applications-bucket storage object. As the trustee, enrol the application. Then delete the 'identity' documents row, which is all api.deleteDocument does for bucket 'applications'. As the trustee, attempt the storage delete and count the affected rows. Then confirm the object still exists and is readable by the trustee, and that applications.files still lists it. As the trustee, delete the student row, check applications.student_id, call enrol_application again and list documents.
- **Conditions:** [authorization_role] A trustee (is_admin) performs the deletion. Only trustees can read the retained copy. [data_state] The document came from enrol_application (bucket 'applications'). Resurrection also needs the student row to be deleted later, through PostgREST or the dashboard (there is no portal button), followed by another enrolment of the same application.
- **Actual result:** The documents count dropped to 0, but the trustee's delete on storage.objects for the applications object affected 0 rows. The object applications|incoming/2222…/id.jpg remained, readable by the trustee, and applications.files still listed it (field idFile). After the student was deleted, the application showed student_id NULL with status 'accepted'. Re-enrolment returned a new student id and recreated 'identity|applications|incoming/2222…/id.jpg'. See agents/v7-deletion/artifacts/evidence-1.txt (this matches the hunter's agents/h8-deletion/artifacts/evidence-1.txt).
- **Impact:** Highly sensitive applicant PII (national ID image, income proof) outlives an explicit deletion and the applicant-facing deletion promise. Access stays limited to trustees, so no unauthorised principal gains read access.
- **Priority:** low. Likelihood: medium (Retention happens every time a trustee deletes any enrolment-derived document (ID, income proof, certificates, photo) through the normal UI, with no unusual conditions. Resurrection also needs a student deletion and a re-enrolment, which the portal UI does not expose.). Impact: low. Confidence: high.
- **Smallest source fix:** Make document deletion bucket-aware and durable. Add a trustee delete policy for the 'applications' bucket. In deleteDocument, remove the object from doc.bucket and check the result, removing the blob before the row or atomically with it (for example through a SECURITY DEFINER delete_document RPC). Also remove the matching element from applications.files, and clear students.photo_path when the photo is deleted. Add an admin 'delete application' operation that removes the applications row, its incoming/ objects and any derived student data, and document the manual purge of the Apps Script Sheet row, Drive folder and emails. Add a regression test: after an application-derived document is deleted, neither storage.objects nor applications.files contains the path, and enrol_application does not recreate it.

## 6. Hardening notes and positive patterns

### Hardening (from hunters; not findings)

- (h6-supply) deploy.yml grants pages:write and id-token:write at workflow level, so the build job (which runs npm ci and the build toolchain) also holds them; scope these permissions to the deploy job only.
- (h6-supply) GitHub Actions are referenced by floating major tags (actions/checkout@v4, setup-node@v4, upload-pages-artifact@v3, deploy-pages@v4); pin to full commit SHAs.
- (h6-supply) .gitignore does not cover .env, .env.*.local or the PII-bearing operator files named in supabase/SETUP.md (import-existing-students.sql, supabase-admins.sql); add them so an operator running setup.mjs from the repo copy cannot commit student data.
- (h6-supply) supabase/setup.mjs honors SUPABASE_API_BASE from the environment, sending the Management API token to any host; restrict to https://api.supabase.com or warn loudly when overridden.
- (h6-supply) supabase/setup.mjs prints the new project's database password to stdout (line 218); terminal scrollback/logging retains it.
- (h6-supply) vercel.json sets X-Frame-Options/nosniff/Referrer-Policy but GitHub Pages (the URL configured as Supabase site_url) cannot set response headers, and neither host sets a Content-Security-Policy; the portal on GitHub Pages is frameable.
- (h6-supply) Runtime background videos default to a third-party CloudFront host (src/content.ts:12-17, .env.example) whose content can change without review; ASSESSMENT.md already flags self-hosting.
- (h6-supply) Snapshot has no .git directory, so git history for committed-then-removed secrets could not be reviewed.
- (h10b-lock-starvation) Narrow the lock: do saveFiles_ (Drive writes) before waitLock, or after releaseLock, and hold the lock only around newReference_ plus appendRow. Use lock.tryLock with a short timeout and a retry instead of failing silently.
- (h10b-lock-starvation) Reject before any expensive work: cap files.length (the site sends at most about 5 + education rows) and the total decoded bytes, and when Supabase is the system of record, ignore files entirely for notification-only posts that carry a valid reference.
- (h10b-lock-starvation) notifyTrustees in src/lib/application.ts is fire-and-forget with no retry or server-side fallback. Any Apps Script failure, starvation included, silently drops trustee notification. A Supabase-side record or trigger, rather than the browser, could drive notification.
- (h5-apps-script) Code.gs:75 accepts any caller-supplied pattern-matching reference with no check against Supabase or existing rows, and Code.gs:211 sets the trustee notification's replyTo to the caller's email; SETUP.md tells trustees to reply to that email. A forged notification can therefore reuse a real applicant's name and reference so trustee replies go to the attacker. Fix: have the Supabase path sign notifications (e.g. HMAC with a script-property secret) and drop or flag unsigned ones.
- (h5-apps-script) Code.gs:156 accepts any image/* MIME (including image/svg+xml) for Drive files; restrict to image/jpeg, image/png, image/webp and application/pdf to match the Supabase bucket.
- (h5-apps-script) Code.gs:209 puts the raw fullName (up to 20000 chars, may contain CR/LF) into the email subject. MailApp is expected to encode headers, but str_ could strip control characters and cap subject length.
- (h5-apps-script) Code.gs:236 cell_ does not prefix a value starting with an invisible character such as U+200B. Sheets does not evaluate it as a formula, but stripping leading format characters would make cell_ robust to future changes.
- (h4-client) Applicant draft PII (name, DOB, phone, email, family situation) persists in localStorage key jvj-application-draft-v2 with no expiry and auto-resumes for whoever opens the Apply journey next in the same browser profile (src/lib/application.ts:83-102, src/journey/Journey.tsx:74-77). Applicants on shared or internet-cafe devices could expose it to the next user. Consider sessionStorage or a short TTL, plus a clear 'not on a shared computer?' control.
- (h4-client) GitHub Pages serves the site at https://freeaami.github.io/Jeevunjee-site/, so its origin is shared with every other GitHub Pages project of the same account. Those projects can read jvj-portal-auth (trustee access and refresh tokens) and the draft PII from localStorage. GoTrue also accepts any redirect on the same hostname. Prefer a dedicated custom domain or the Vercel deployment for the portal.
- (h4-client) No frame-ancestors or X-Frame-Options protection is possible on the GitHub Pages deployment (only Vercel sets X-Frame-Options: DENY). Clickjacking is currently blocked only by browser third-party storage partitioning, which leaves a framed portal unauthenticated. Serving the portal only from a header-capable host would remove that dependency.
- (h4-client) updatePassword (src/portal/api.ts:149) changes the password with only the current session and no reauthentication. Consider enabling Supabase 'Secure password change' (reauthentication nonce) so a stolen session cannot take over a trustee account permanently.
- (h4-client) Applicant-controlled JSON in applications.answers/files is rendered without type checks in some places, for example {e.level} in Applications.tsx and f.label || f.name. A non-string object value makes React throw and breaks that trustee application view. This is an availability nuisance, not XSS. Coerce with str() everywhere.
- (h8-deletion) src/portal/api.ts:258-262: deleteDocument deletes the documents row before the storage remove and ignores the remove error. On a transient failure an orphan blob stays under files/students/<id>/ and the student can still list and read it through the path-based 'jvj students read own' policy. Remove the blob first and check the result.
- (h8-deletion) src/portal/api.ts:210-214: setStudentPhoto replaces photo_path without removing the previous object, so old photos accumulate in files/students/<id>/ (still readable by that student and trustees).
- (h8-deletion) Deleting the 'photo' document does not clear students.photo_bucket/photo_path set by enrol_application (schema.sql:337-338), so trustees still see the 'deleted' photo in the student file.
- (h8-deletion) No in-product operation deletes an application, a student, or any applications/incoming/* object, even though Journey.tsx:491 promises deletion on request. A student row deleted through PostgREST cascades to documents but leaves every storage object under files/students/<id>/ and applications/incoming/. A documented operator purge procedure (or RPC) is needed.
- (h9-enumeration) Make sign-up responses uniform. For example, route account creation through an RPC or an Edge Function that validates the access code or allow-list first and always returns the same generic message. Alternatively, turn on 'Confirm email' or GoTrue's obfuscated signup response and handle confirmation through the access-code flow.
- (h9-enumeration) Sign-in already returns one generic message for wrong email and wrong password (api.ts:50); keep it that way.
- (h1-anon-db) submit_application accepts any path matching ^incoming/<36 hex-or-dash>/<name>, including another applicant's object path. enrol_application copies it into documents, and the 'jvj students read own application files' storage policy would then let the enrolled student read that object. The other applicant's random UUID folder is not disclosed to anon, so this is not exploitable now. Binding paths to a server-issued upload folder would close it.
- (h1-anon-db) enrol_application casts applicant-controlled dateOfBirth, durationYears, totalFee*, plan amounts and file size with ::date, ::numeric and ::bigint without guarding them. A malformed value makes enrolment of that same application fail, which needs trustee cleanup but has no cross-principal effect.
- (h1-anon-db) Supabase's default privileges and PostgreSQL's PUBLIC execute make every public function executable by anon. Only random_code is revoked. Explicitly revoking execute on is_admin, my_student_id, enrol_application, issue_access_code and the trigger functions from anon would shrink the surface, though each is currently safe.
- (h3-rls) Applicant-claimed storage paths are not bound to their uploader. submit_application (supabase/schema.sql:298) accepts any path matching incoming/<36 hex>/<name>. enrol_application (supabase/schema.sql:382-385) copies those paths into documents, and the storage policy 'jvj students read own application files' (supabase/schema.sql:497-501) then grants the enrolled student read access to whatever object each path names. It was shown locally that a student can read another applicant's ID image if the student knows that applicant's random folder UUID (evidence-1 CHECK1). Fix: require every path in one submission to share a single folder, reject a folder that any existing application already references, and in enrol_application skip any path referenced by another application.
- (h3-rls) Revoking access has to be done by hand outside the app. Removing an email from admin_emails does not demote an existing admin profile (CHECK4). Profiles has no admin UPDATE or DELETE policy (supabase/schema.sql:424), so no trustee can revoke a student login or another trustee from the portal. Student status 'withdrawn' or 'completed' is not part of any RLS predicate (CHECK2). Consider adding an admin-only revoke_login RPC that deletes the profile and the auth user, and optionally adding status = 'active' (or not 'withdrawn') to my_student_id().
- (h3-rls) Students can read access_code and access_code_expires on their own students row (supabase/schema.sql:436). That includes a code a trustee issued 'for another login' (src/portal/admin/StudentFile.tsx:544). The impact stays within the same student file. Column-level grants or a view could hide these columns from students.
- (h3-rls) Deleting a student keeps the source applications row with its full PII (applications.student_id is set to null) and leaves orphaned storage objects under files/students/<id>/ and applications/incoming/<folder>/. These are readable only by admins, but ASSESSMENT.md tells applicants they can ask for deletion, and the app has no deletion path that removes these copies.
- (h7-submit-flood) Add a pg_column_size(p_files) byte cap (and ideally a per-element size cap) in submit_application mirroring the existing 200 kB p_answers guard; file elements only need {field,label,name,path,mime,size}, so reject or strip unknown keys and bound mime/name/label lengths before insert.
- (h7-submit-flood) Add server-side pagination/limits to the trustee application reads (src/portal/api.ts:166 and 276 use select('*') with no limit); select only columns needed for the list view rather than the full answers/files jsonb, and lazy-load a single application's detail on navigation.
- (h7-submit-flood) Consider a lightweight anti-automation/rate control on anonymous submit_application (e.g. per-IP throttling at the edge or a proof-of-work/captcha gate) and a periodic cleanup/archival of stale 'new' applications to bound table cardinality; these are deployment-layer mitigations referenced here as hardening, not findings.
- (h2-storage) submit_application (supabase/schema.sql:297-299) accepts any 'incoming/<uuid>/<name>' path without checking that the caller uploaded it or that it exists. enrol_application (schema.sql:374-386) then grants the enrolled student read access to it via 'jvj students read own application files' (schema.sql:497-501). Not exploitable today because other applicants' random folder UUIDs are never exposed to non-admins. Fix: issue the folder server-side, or have submit_application check that storage.objects rows exist and that each path's folder is unique to one application.
- (h2-storage) Bucket allowed_mime_types 'image/*' (schema.sql:464) admits image/svg+xml, and MIME limits trust the client-declared Content-Type. Trustees open applicant files via signed URLs in a new tab (src/portal/admin/StudentFile.tsx:307-313), on the Supabase storage origin, not the portal origin. List explicit raster types (image/jpeg, image/png, image/webp, image/heic) and serve with Content-Disposition: attachment (createSignedUrl download option). The rendering path itself belongs to the peer openFile DOM-XSS unit.
- (h2-storage) Signed URLs live for 30 minutes (src/portal/api.ts:265) and stay valid after a document is deleted or a student login is removed. A shorter TTL (for example 60-300 s) narrows the window. The module-level urlCache (src/portal/ui.tsx:202-219) never expires entries, so avatars break after 30 minutes in a long-lived tab (functional, not a disclosure).
- (h2-storage) Authenticated students can upload unlimited 15 MiB objects into files/students/<own id>/ without creating a documents row (schema.sql:491-494). This is limited to a small semi-trusted population and trustees can delete them (schema.sql:482-484), but a per-student cap or orphan sweep would bound it.

### Positive source patterns

- RLS is enabled on every public table. Policies key on `my_student_id()` / `is_admin()`, which are SECURITY DEFINER with a pinned `search_path`. Students have no UPDATE or DELETE anywhere, and the repository's own 64-check RLS suite passed unmodified.
- Access codes come from a CSPRNG (`gen_random_uuid` bytes, unbiased 32-character alphabet). They are single-use, expire after 14 days and are consumed under `FOR UPDATE`.
- `submit_application` writes only server-chosen columns and returns only the reference. Anonymous callers cannot read anything back.
- Apps Script neutralises spreadsheet formulas (`cell_`) and HTML-escapes everything in emails. The client has no `innerHTML` or `eval` sinks, and React escapes all applicant text.
- Only the public anon key is committed. The build uses `npm ci` against a lockfile in which every package has an integrity hash. Workflows run only on trusted events.

## 8. Remediation status (commit `045bf1a`, after this audit)

This section is outside the audited snapshot and does not change any verdict above. The fixes are tested by `supabase/tests/run_security_tests.py` (105 checks pass) and by a mocked Apps Script harness. Nothing was tested against the live deployment.

|---|---|
